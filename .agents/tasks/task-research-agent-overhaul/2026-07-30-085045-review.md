# RAG pipeline overhaul: real embeddings, agent skills, production middleware

This change replaces the hash-based placeholder embedding in a FastAPI "Deep Research Agent" with a working TF-IDF + SVD vectorization pipeline, adds five agent skills (summarization, comparison, extraction, web search, multi-turn conversation), layers on production middleware (error handling, request IDs, structured logging, rate limiting, CORS), and delivers a 97-test suite. The result transforms a non-functional skeleton into a working local-first RAG system that operates without external API keys. Watch for: all state lives in-process memory with no eviction (confirmed), the TF-IDF vectorizer must refit the entire corpus on every ingest which becomes O(n^2) as documents grow (confirmed), conversation history and rate-limit state are lost on restart with no indication to the caller (confirmed), and the `ensure_project_access` error path conflates "project not found" with "access denied" at the HTTP layer giving 403 for missing projects (confirmed).

**Verdict**: APPROVED

## High-level view

The embedding system replaces a hash-scatter function with TF-IDF + TruncatedSVD producing 128-dim dense vectors. Every ingest call refits the vectorizer on the full project corpus and re-embeds every existing chunk, making write cost linear in total corpus size and overall ingest cost quadratic in document count.

Chunking moved from paragraph-boundary splitting to a 512-char sliding window with 100-char overlap. When the window adjusts to a word boundary, the overlap subtraction still uses the pre-adjustment end position, causing actual overlap to vary by a few characters per chunk.

The five skills (summarizer, comparator, extractor, web search, conversation) are self-contained modules with no shared state except the conversation singleton. They re-parse raw files from disk on every call through `_get_project_file_texts`, bypassing the already-chunked text stored in memory.

The `VectorizerStore` singleton holds one vocabulary for the entire process. In multi-project usage, the last project to ingest overwrites the vocabulary, silently degrading retrieval quality for all other projects.

Starlette's `BaseHTTPMiddleware` (used by all three custom middleware) buffers entire response bodies. This precludes adding streaming endpoints without replacing the middleware implementation.

The test suite covers every endpoint and skill module, mocking external calls. Every test file independently resets all store dictionaries — if a new collection is added to `InMemoryStore`, all test files must be updated in lockstep.

<summary>Issues (7)</summary>

1. **Quadratic reindex on ingest** — Every call to `/api/ingest/{file_id}` calls `refit()` on all project chunk texts then `reindex_embeddings()` which re-embeds every chunk. For N documents this is O(N^2). Add incremental vectorizer updates or defer refit to a background task. (confirmed)
2. **Unbounded in-memory state** — `InMemoryStore` accumulates projects, chunks, conversations, and retrieval logs without eviction. Long-running instances will OOM. Add TTL-based eviction or persistence. (confirmed)
3. **403 for missing projects** — `ensure_project_access` raises `PermissionError("Project '...' not found")` which the endpoints translate to HTTP 403. A missing project should return 404. Split the check into existence (404) and authorization (403). (confirmed)
4. **Conversation history unbounded** — `ConversationManager` stores all turns forever. No cap on turns per conversation and no cap on total conversations. Add a `max_turns` limit or summarization step. (confirmed)
5. **BaseHTTPMiddleware streaming limitation** — Starlette's `BaseHTTPMiddleware` buffers the entire response body, breaking streaming. If streaming endpoints are added later, the middleware stack will silently buffer or error. Document or switch to pure ASGI middleware. (likely)
6. **Re-parsing files on every skill call** — `_get_project_file_texts` re-reads and re-parses file content from disk on every summarize/compare/extract request. Cache parsed text in the `FileRecord` or store. (confirmed)
7. **VectorizerStore singleton shared across projects** — The singleton `VectorizerStore` holds a single vocabulary fitted from whatever project was last ingested. In a multi-project deployment, projects pollute each other's vocabulary. Scope the vectorizer per project. (confirmed)

## TF-IDF + SVD embedding scaling

The ingest endpoint refits and reindexes on every call:

```python
all_texts = store.get_all_chunk_texts(file_record.project_id)
refit(all_texts)
store.reindex_embeddings(file_record.project_id)
```

`reindex_embeddings` iterates `project_chunks` and calls `embed()` on every chunk. For a project with 1000 chunks adding one more document, this means fitting a vectorizer on ~1010 texts and then transforming all 1010. The tenth document ingested pays for all previous documents.

The fallback path (corpus < 2 documents) uses the old hash-scatter approach, meaning the first uploaded document gets hash embeddings and only on the second ingest do all chunks get meaningful vectors.

## Sliding window overlap drift

When `end < text_len` and the break adjustment shortens the chunk to a word boundary, the next chunk's start is computed as `end - overlap` using the *original* `end`, not the adjusted one:

```python
if end < text_len:
    last_space = chunk_text.rfind(" ")
    if last_space > chunk_size // 2:
        end = start + last_space
        chunk_text = text[start:end]
...
start = end - overlap if end < text_len else text_len
```

After the adjustment, `end` is smaller but `overlap` stays at 100. The actual overlap between consecutive chunks varies depending on where word boundaries fall. This doesn't break retrieval but makes `start_offset`/`end_offset` metadata less precise for citation highlighting.

## VectorizerStore singleton is project-agnostic

```python
class VectorizerStore:
    _instance: Optional["VectorizerStore"] = None
    ...
    def refit(self, corpus: list[str]) -> None:
        self._corpus = corpus
        ...
```

The `refit()` call receives texts from one project and replaces the global vocabulary. The second project's refit overwrites the vocabulary the first project's embeddings were computed against, making the first project's stored embeddings stale relative to the current transform. Any multi-project usage will silently degrade retrieval quality.

## Conversation memory has no eviction

```python
class ConversationManager:
    def __init__(self) -> None:
        self.conversations: dict[str, Conversation] = {}
```

No TTL, no max-conversations cap, no max-turns-per-conversation limit. `get_context` limits what's *returned* to callers (`max_turns=10`), but the underlying storage is never pruned. Each turn stores the full assistant response text, so memory grows proportionally to total query volume.

## 403 vs 404 conflation in access control

```python
if project is None:
    raise PermissionError(f"Project '{project_id}' not found")
if user_id not in project.members:
    raise PermissionError("User does not have access to this project")
```

All endpoint handlers catch `PermissionError` and return 403. A client cannot distinguish between a typo in the project ID and an actual authorization failure. The `share_project` endpoint handles this correctly (checks existence separately and returns 404), but the generic `ensure_project_access` pattern used everywhere else does not. This also leaks project existence information — a 403 for a valid project vs 403 for a nonexistent one gives the same signal to an attacker.

## Re-parsing files on skill calls

```python
def _get_project_file_texts(...):
    for f in store.files.values():
        ...
        text, _ = parse_content(f.local_path, f.mime_type)
        results.append((f.filename, text))
    return results
```

For PDF/DOCX files this re-runs the parser on every summarize/compare/extract request. The parsed text is already available in chunks (stored in `store.chunks`), but the skill endpoints bypass that and go back to raw files. This is both slower and fragile when `local_path` is empty (as in test scenarios where chunks are added directly without writing files to disk).

## Web search: scraping fragility and ToS

The `WebSearchProvider` parses DuckDuckGo's HTML using regex for CSS classes (`result__a`, `result__snippet`). Layout changes will break parsing silently (empty results, no crash). The `requests.post` call uses a spoofed browser User-Agent. DuckDuckGo's terms prohibit automated access; acceptable for local dev but needs replacement (DuckDuckGo API, SearxNG, or Brave Search API) before any public deployment.
